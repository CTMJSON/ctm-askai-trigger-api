# Updating AskAI Instructions via the CTM API

**Audience:** Agency / multi-account administrators
**Scope:** Read and update the instructions on an existing AskAI capture action, for any sub-account your agency key can reach.

This guide covers the one operation that is easy to get wrong and hard to notice
you got wrong: changing the instructions text on an AskAI action without
disturbing the rest of its configuration.

---

## 1. Before you start

You need two things.

| Item | Where to get it | Used as |
|---|---|---|
| **Agency API key** | CTM → Settings → API (agency level). Sent as HTTP Basic auth. | `$CTM_KEY` |
| **Sub-account ID** | The numeric account id of the sub-account you are editing. Visible in the URL when logged into that account. | `$ACCOUNT_ID` |

The same agency key works for every sub-account you administer — you change the
account id in the URL, not the key. If your key is scoped to a single account,
requests against any other account id will return `404`.

### Naming conventions used below

```bash
export CTM_KEY='your_agency_key_here'
export ACCOUNT_ID='your_subaccount_id_here'
export TRIGGER_ID='AUT...'        # from the trigger URL in the app
```

> The trigger URL in the browser looks like
> `https://app.ctm.com/triggers/AUT...`. The long `AUT...` string at the end is
> the **trigger id** — that is the value you put in `TRIGGER_ID`. Do not retype
> it; copy it. Trigger URLs can be saved and shared, so confirm the one you are
> holding matches the trigger you intend to change.

## 2. The API pattern

All requests use the same base:

```
https://api.calltrackingmetrics.com/api/v1/accounts/{ACCOUNT_ID}
```

### Read the trigger

```bash
curl -s -u "$CTM_KEY" \
  -H 'Accept: application/json' \
  "https://api.calltrackingmetrics.com/api/v1/accounts/$ACCOUNT_ID/triggers/$TRIGGER_ID"
```

A successful read returns `200` with the full trigger object. Save it — you will
need the whole thing in step 4.

```bash
curl -s -u "$CTM_KEY" \
  -H 'Accept: application/json' \
  "https://api.calltrackingmetrics.com/api/v1/accounts/$ACCOUNT_ID/triggers/$TRIGGER_ID" \
  > trigger_before.json
```

### Update the trigger

```bash
curl -s -u "$CTM_KEY" -X PATCH \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json' \
  -d @trigger_payload.json \
  "https://api.calltrackingmetrics.com/api/v1/accounts/$ACCOUNT_ID/triggers/$TRIGGER_ID"
```

Success returns `200` with `{"status":"success","id":"AUT...","object":{...}}`.

## 3. Where the instructions live

The instructions text is here:

```
routing_rules[].actions[].ask_question
```

It is a plain string on the action itself — not nested inside a config object.

A typical AskAI action looks like this:

```json
{
  "id": 1234567,
  "type": "ai_capture",
  "class": "TriggerAiCaptureV2",
  "label": "AskAI",
  "conditions": [],
  "ask_question": "Extract the first name of the salesperson ...",
  "capture_to_field": "custom_fields.example_field",
  "capture_fields": null,
  "capture_field_descriptions": {"custom_fields.example_field": ""},
  "include_parts": "agent",
  "system_messages": "[\"\"]",
  "no_conversation": null,
  "no_refinement": null,
  "normalize_speaker_labels": true,
  "max_output_tokens": "",
  "input_via_audio": null
}
```

Things worth knowing about this object:

- **Line endings.** `ask_question` uses CRLF (`\r\n`). If you rewrite the prompt by
  hand, keep them, or the text will run together in the UI.
- **`preview_text` is generated by CTM.** It summarises the prompt and the target
  field. You do not send it; it refreshes itself when the prompt changes.
- **`conditions`: `[]` means "always run".** Leave it alone unless you intend to
  change when the action fires.
- **Find your action**, don't assume its position. A trigger can hold multiple
  routing rules and multiple actions each. Locate the one where
  `type == "ai_capture"` (and, if there is more than one, match on `id`).

---

## 4. ⚠️ The one rule that matters

**`PATCH` replaces the action object. It does not merge.**

If you send an action containing only `id`, `type` and `ask_question`, every field
you left out is set to **null** — and the request still returns `200`. Nothing
warns you.

What that breaks:

| Omitted field | Result |
|---|---|
| `capture_to_field` | **Set to null — AskAI stops writing its answer anywhere.** The trigger appears to run and produces nothing. |
| `include_parts` | Set to null — loses the agent-only scope, so caller speech gets analysed too |
| `system_messages` | Reset to `[]` |
| `normalize_speaker_labels` | Reset |
| `max_output_tokens` | Reset |

The failure is silent in the worst possible way: the trigger stays enabled, keeps
running on every call, and quietly writes nothing.

### The safe pattern

1. **GET** the trigger.
2. **Change only** `ask_question` inside the object you just received.
3. **PATCH the whole object back**, unmodified except for that one field.

Because you are replaying what the API gave you, every other field keeps its
current value.

```bash
# 1. read
curl -s -u "$CTM_KEY" -H 'Accept: application/json' \
  "https://api.calltrackingmetrics.com/api/v1/accounts/$ACCOUNT_ID/triggers/$TRIGGER_ID" \
  > trigger_before.json

# 2. edit only ask_question, in place
python3 - <<'PY'
import json
t = json.load(open("trigger_before.json"))
for rule in t.get("routing_rules", []):
    for act in rule.get("actions", []):
        if act.get("type") == "ai_capture":
            act["ask_question"] = open("new_instructions.txt").read()
json.dump(t, open("trigger_payload.json", "w"), indent=1)
PY

# 3. write the full object
curl -s -u "$CTM_KEY" -X PATCH \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d @trigger_payload.json \
  "https://api.calltrackingmetrics.com/api/v1/accounts/$ACCOUNT_ID/triggers/$TRIGGER_ID"
```

### Minimum shape if you build the action yourself

Each action **must** include `type`, or the request fails with:

```json
{"status":"error","errors":{"routes[0].actions[0].type":["Invalid action type ''"]},"reason":"Invalid action type"}
```

Minimum accepted is `{id, type}`. **Do not stop there** — see the table above.
Send the complete object.

## 5. Other things that will trip you up

**There are no sub-resource endpoints.** Every one of these returns
`404 {"error":"invalid request"}`:

```
/triggers/{id}/routing_rules
/triggers/{id}/routing_rules/{rule_id}
/triggers/{id}/routing_rules/{rule_id}/actions
/triggers/{id}/routing_rules/{rule_id}/actions/{action_id}
```

Everything goes through the parent `/triggers/{id}` object. Do not waste time
hunting for a per-action route.

**No dry-run or validate endpoint.** The only safe preview is: GET → apply your
change to a local copy → diff → then PATCH. Always snapshot before writing.

**`normalize_speaker_labels` comes back as `'1'`** after any write instead of
`true`. It is the same setting, retyped as a string. Harmless, but expect your
diff to show it and do not "fix" it.

**Some fields are legitimately `null`.** `capture_fields`, `no_refinement`,
`no_conversation`, `input_via_audio` are normally null. Null there is correct.

**`PUT` vs `PATCH`.** Use `PATCH`. `PUT` was not verified for partial-object
behaviour and should be assumed at least as destructive.

**Nothing to publish.** Updating via the API did not disable the trigger or alter
its enabled state, and no separate publish/activate step was required. Confirm
the trigger's `always_run` and `position` values are unchanged after your write.

---

## 6. Response codes

| Code | Meaning |
|---|---|
| `200` | Applied. Response includes the updated object. |
| `400` | Validation error. Read `errors` — the keys are field paths such as `routes[0].actions[0].type`. |
| `404` | Wrong path, or the trigger/account id does not exist, **or your key is not scoped to that sub-account.** |
| `401` / `403` | Credential problem — bad key, or the key lacks write access to triggers. |

A `404` on a sub-account you can see in the app almost always means the key you
are using is account-scoped rather than agency-scoped.

## 7. Verify your change

Do not trust the `200`. Read it back.

```bash
curl -s -u "$CTM_KEY" -H 'Accept: application/json' \
  "https://api.calltrackingmetrics.com/api/v1/accounts/$ACCOUNT_ID/triggers/$TRIGGER_ID" \
  > trigger_after.json

python3 - <<'PY'
import json
b = json.load(open("trigger_before.json"))["routing_rules"]
a = json.load(open("trigger_after.json"))["routing_rules"]

def acts(rules):
    return {x["id"]: x for r in rules for x in r.get("actions", [])}

ba, aa = acts(b), acts(a)
for aid in ba:
    changed = [k for k in ba[aid] if ba[aid][k] != aa.get(aid, {}).get(k)]
    print(f"action {aid}: changed fields -> {changed or 'none'}")

# the fields that must never have been nulled
for aid, act in aa.items():
    for f in ("capture_to_field", "include_parts"):
        print(f"  {aid}.{f} = {act.get(f)!r}")
PY
```

You want to see **only `ask_question`** in the changed-fields list (plus
`preview_text`, which CTM regenerates, and possibly the
`normalize_speaker_labels` retyping). Anything else means you dropped a field —
restore from `trigger_before.json` and try again.

### Rollback

`trigger_before.json` is a complete, valid payload. To undo:

```bash
curl -s -u "$CTM_KEY" -X PATCH \
  -H 'Content-Type: application/json' -H 'Accept: application/json' \
  -d @trigger_before.json \
  "https://api.calltrackingmetrics.com/api/v1/accounts/$ACCOUNT_ID/triggers/$TRIGGER_ID"
```

Keep that snapshot until you have confirmed the new instructions behave as
expected on real traffic.

## 8. Working across multiple sub-accounts

Because the key is agency-level and only the account id changes, the same script
can walk every sub-account you administer.

```bash
#!/usr/bin/env bash
set -euo pipefail

TRIGGER_ID="${1:?usage: update.sh <TRIGGER_ID> <ACCOUNT_ID> [<ACCOUNT_ID>...]}"
shift

for ACCOUNT_ID in "$@"; do
  echo "== account $ACCOUNT_ID =="
  curl -s -u "$CTM_KEY" -H 'Accept: application/json' \
    "https://api.calltrackingmetrics.com/api/v1/accounts/$ACCOUNT_ID/triggers/$TRIGGER_ID" \
    > "before_$ACCOUNT_ID.json"

  python3 - "$ACCOUNT_ID" <<'PY'
import json, sys
acct = sys.argv[1]
t = json.load(open(f"before_{acct}.json"))
n = 0
for rule in t.get("routing_rules", []):
    for act in rule.get("actions", []):
        if act.get("type") == "ai_capture":
            act["ask_question"] = open("new_instructions.txt").read()
            n += 1
assert n == 1, f"expected 1 ai_capture action, found {n}"
json.dump(t, open(f"payload_{acct}.json", "w"), indent=1)
PY

  curl -s -u "$CTM_KEY" -X PATCH \
    -H 'Content-Type: application/json' -H 'Accept: application/json' \
    -d "payload_$ACCOUNT_ID.json" \
    "https://api.calltrackingmetrics.com/api/v1/accounts/$ACCOUNT_ID/triggers/$TRIGGER_ID"
  echo
done
```

Two cautions for the multi-account case:

- **Trigger ids are per-account.** The same logical automation has a different
  `AUT...` id in each sub-account. Loop over `(account, trigger)` pairs, not one
  trigger id.
- **Run one account first, verify it, then proceed.** A mistake here is silent
  and applies to every account you touch.

### A note on instruction content across accounts

If your sub-accounts share an identical automation, the *structure* of the
instructions can be shared. Account-specific values — staff names, locations,
product lines — cannot. If you keep a per-account list inside the instructions,
plan for how it gets updated when that list changes, because the API will happily
write a stale one. Consider whether a per-account field or a separate trigger per
location is a better fit than one shared prompt with an embedded name list.

## 9. Quick reference

```
READ     GET   /accounts/{account_id}/triggers/{trigger_id}
UPDATE   PATCH /accounts/{account_id}/triggers/{trigger_id}

Auth     -u "$CTM_KEY"                        (HTTP Basic)
Headers  Content-Type: application/json
         Accept: application/json

Prompt   routing_rules[].actions[].ask_question     (CRLF line endings)
Required every action must carry "type"
Safe     GET -> edit only ask_question -> PATCH whole object -> GET to verify
Never    send a partial action object
```

**The one-line version:** read the whole trigger, change the one field, send all
of it back — and read it again afterwards to make sure nothing went missing.
